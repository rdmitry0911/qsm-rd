QSM Direct shared23: adaptive QSV / VA-API, 2026-10-18

Implementation
--------------
The existing shared VM/LXC controller now enables all seven supported
encoders: libx264, H.264/HEVC NVENC, H.264/HEVC QSV and H.264/HEVC VA-API.
The common configurable ceiling, multi-viewer rate, RTCP feedback, pacing,
hysteresis and on-demand recovery from shared21/shared22 remain in place.
There is no periodic half-second IDR refresh and no guest-side bitrate API.

QSV uses libavcodec with NV12 input, async_depth=1, no lookahead/B-frames,
forced recovery IDRs and a 65535-frame GOP (the SDK's 16-bit infinite value).
The existing AVCodecContext rate fields trigger FFmpeg's documented QSV
rate reset. FFmpeg/QSV may reject settings which the actual hardware cannot
support; automatic H.264 policy retains the explicit software fallback,
while hardware-only policy still reports failure. No software result is
presented here as a successful Intel hardware test.

FFmpeg 7 VA-API caches its rate-control parameters at codec initialization.
Merely changing AVCodecContext.bit_rate would update the label but leave
the actual stream unchanged. VA-API therefore uses in-process hardware
frames and reopens only its codec at a material target change. It retains
the DRM device, upload pool, BGRA conversion, source PTS counter, Unix taps
and WebRTC peer. Pending output is drained across that boundary. The new
codec begins with an IDR; a PLI alone forces an IDR without a codec reopen.
The rate controller's stability gates limit unnecessary quality changes.
Real network-driven changes can still briefly change image quality.

VA-API/QSV devices are opened before an LXC worker drops root. Subsequent
codec setup, resize, encoding and reset reuse that AVBufferRef as nobody;
there is no host render-group or render-node permission change. An automatic
hardware initialization failure can fall back to libx264. The executable
launcher remains available when libavcodec is not built, including applying
changed rate settings on its process replacement; official debs use the
in-process implementation. Hardware capability probes now use the matching
bounded rate/low-delay options instead of unbounded QSV/VA-API defaults.

Hardware encoder probes
-----------------------
build-probe.py extracts the exact production LibavVideoEncoder class. It is
compiled against Trixie libavcodec/libavutil/libswscale and run on the AMD
node. The DRM device is opened as root, then all supplementary groups are
cleared and uid/gid become 65534 before codec construction, resize-equivalent
setup, encoding, IDR requests and bitrate resets. This exercises the LXC
privilege boundary rather than accidentally testing only a root encoder.

Dynamic 1280x800/60: 1200 frames, 8 -> 2 -> 12 -> 0.5 Mbit/s changes at
frames 301/607/913, explicit IDRs at 7/17/49. H.264 and HEVC VA-API each decode
all 1200 frames with seven keys (initial + three requests + three rate
boundaries). Maximum observed combined reconfiguration/encode time in the
H.264 run was 30.31ms; HEVC 11.90ms. The legacy 300-frame throughput print
boundaries do not exactly match the new unaligned changes, so those segment
numbers are diagnostics rather than exact per-target averages. Low target
overshoot remains a hardware limitation, especially for complex H.264.
Explicit max-QP=51 was separately tried and did not improve it; it is not
part of the production change. Reduce display size/FPS on links below the
hardware's practical minimum; this release does not add resolution/FPS
adaptation or promise an exact wire-rate cap.

Static 1970x1220/60, 8Mbit/s: 600 frames, explicit IDR at347. Both AMD codecs
decode every frame and emit exactly two keys. As in the shared22 text check,
steady-state luma metrics exclude initial frames0..90 and the explicitly
requested recovery window347..437. H.264 peak mean text-region luma delta
0.03933/255; HEVC0.002043/255. Neither crosses the0.15 threshold. The recovery
window is not excluded from decoding or keyframe counts.

Regression: the same new class is separately run on the NVIDIA node with
H.264 NVENC, HEVC NVENC and libx264. All decode1200 frames across the same
unaligned rate changes and forced IDRs. NVENC has7 keys, software4 as expected.
No package/service or live CT105 desktop was changed on that node.
