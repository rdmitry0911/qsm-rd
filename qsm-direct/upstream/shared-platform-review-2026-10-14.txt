Ownership and protocol
qemu-server starts one dbus-daemon before QEMU in the VM's scope. It cleans
socket/daemon at VM stop/failure and protects against stale reused PIDs.
The socket is root-owned mode0600 at /run/qemu-server/VMID.dbusdisplay.
QSM never provisions/deletes that bus. Its service restart retires its own
sessions and leaves QEMU's bus intact; reopening the console reconnects.
Protocol v2 is one root-only Unix request, no SCM_RIGHTS descriptor:
  {version:2,vmid:VMID,user:PVE_USER,offer:{sdp:..., ...}}
Settings requests replace offer with settings:null (read) or
settings:{codec:auto|h264|hevc,encoder:auto|hardware|software} (write).
VMID and the root-owned running config derive the bus path independently;
old saved addresses cannot redirect a native VM. The service checks SO_PEERCRED.
Legacy v1 FD attachment remains supported, outside the native shared path.
PVE authorizes all browser routes; the media service does not parse tickets.
Native signalling uses port8006, while media still requires reachable UDP.
Console-only status returns running/stopped, not the full VM.Audit payload.
Policy updates preserve node-local explicit encoder/render-node choices.

Review boundaries
Top-level dbus-display naming, bus policy, audio defaults and API/UI choices
need maintainer review. Full Kyber/RDP services/browser and runtime Venus
were not qualified here. The NVIDIA patch's previous adapter-to-file test
must not be described as a full Kyber integration test. Concurrent display
capture is proven, not concurrent clipboard ownership: QEMU allows a single
clipboard proxy. Native clipboard was checked with spice-vdagent on X11;
the retained QSM companion supports existing desktop integrations but a new
Wayland end-to-end clipboard qualification was not part of this run.
Performance figures in older documents refer to their original setups and
were not remeasured as benchmarks of the shared-platform revision.

Production follow-up: shared4, 2026-10-14
Installed on 192.168.64.20 after shared3. VM103 was migrated/restarted with
explicit user authorization; VM104 and containers remained running.
An actual user connection through VPN timed out after 20 seconds; capture
continued normally. The old client incorrectly labelled every lost peer
or data channel as a stopped VM. shared4 verifies status before that label,
keeps the viewer and offers Reconnect when the VM is running or status is
unknown. ICE gathering now waits for completion or a bounded 10-second
fallback with candidates; the listener survives the initial gathering
transition. Candidate-free offers are rejected with browser/VPN guidance.
Behavior tests cover running/stopped/unavailable status, repeated shutdown
events, and gathering transitions/completion/timeout. They pass.
Commit: 1b2864d. Patch: patches/qsm-shared-consumer/0002-*.patch.

A separate Chrome 145 browser on the LAN connected to the native API bridge
and decoded video for over30 seconds. Signalling in that diagnostic runner
used root CLI API calls, not a browser user's authentication fixture; UDP,
DTLS/SRTP and Chrome's H.264 decoding crossed the real LAN. This verifies
browser/media connectivity on the LAN, not the user's VPN path.
The VPN client still requires its own retest; do not claim that updating
shared4 proves its UDP path or browser permissions are correct.
