Intel Iris Xe qualification, 2026-10-19
======================================

Target: dima@172.16.16.200, Ubuntu 24.04.4, kernel 6.8.0-146-generic,
Core i7-13800H / Raptor Lake-P Iris Xe 8086:a7a0, i915 renderD129.
The other render node is NVIDIA. The Intel GPU is used by SDDM/Xorg.
No physical GPU was detached, graphical session stopped or existing VM
restarted. Intel hardware results below run on the Ubuntu host, not in
nested Proxmox. GPU passthrough into Proxmox awaits the operator's answer
about temporarily stopping the Intel login screen. SR-IOV reports 7 possible
VFs, but this stock i915 module has no max_vfs facility and creates no VFs.
No replacement kernel/driver is installed on the Ubuntu host.

Two fixes
---------
1. QSV opens and encodes correctly, but FFmpeg's live reset rejects the
   first 8 -> 2 Mbps transition: MFX_ERR_INCOMPATIBLE_VIDEO_PARAM (-14).
   Its requested HRD/VBV size changes with bitrate. Updating initial buffer
   occupancy as well did not fix the reset. QSV now drains/reopens just its
   codec, as VA-API already does, retaining the prepared device, conversion,
   source timestamps and WebRTC peer. No root privileges are restored.
2. Intel HEVC VA-API with AUD enabled emits an escaped Annex B prefix in
   later packets, e.g. 00 00 03 00 01 46 ... . The software decoder reports
   'No start code is found'. Omitting redundant AUDs fixes all tested frames.
   In-process packets already delimit access units. Only hevc_vaapi changes;
   H.264, QSV, NVENC and the external-process fallback retain their options.
   The HEVC VA-API capability probe uses the matching AUD=0 setting.

Exact production class
----------------------
build-probes.py extracts LibavVideoEncoder from the current media worker.
The generated C++ sources are included. Build in Debian Trixie with:
  g++ -std=c++20 -O2 encoder-probe.cpp -o encoder-probe \
      $(pkg-config --cflags --libs libavcodec libavutil libswscale)
  g++ -std=c++20 -O2 static-probe.cpp -o static-probe \
      $(pkg-config --cflags --libs libavcodec libavutil libswscale)
Set QSM_PROBE_VAAPI_DEVICE to the intended render node. QSV deliberately
uses its default Intel device selection, not a DRM path interpreted as a
QSV implementation name. Dynamic probes take CODEC 8000 nobody. Static
probes always drop privileges and read fixture.bgra in their working directory.
The fixture is the existing review-keyframe-stability-2026-10-17 image.

The Ubuntu host runs these Trixie libraries in an isolated chroot under
/var/tmp/qsm-intel-lab/runtime, with host /dev and read-only /sys bind mounts:
libavcodec61 7:7.1.5-0+deb13u1, libvpl2 1:2.14.0-1+b1,
libmfx-gen1.2 25.1.4-1, intel-media-va-driver-non-free 25.2.3+ds1-1.
Dependencies are copied from the existing media builder, not installed over
the Ubuntu host libraries. Device creation runs as root, then supplementary
groups are cleared and uid/gid become 65534 before codec construction,
encoding, requested keyframes and rate changes. No render permissions or
host group membership are changed. There is no software encoder fallback
in these explicit hardware probes.

Results
-------
Dynamic 1280x800/60, 1200 synthetic frames, target changes at301/607/913:
8 -> 2 -> 12 -> 0.5 Mbps, explicit IDRs at7/17/49. Intel H.264 QSV,
H.264 VA-API, HEVC VA-API and HEVC QSV each decode all1200 frames and have
7 keys: initial, three explicit recovery requests, three codec boundaries.
The probes check each requested keyframe and one packet per source frame.
Combined maximum setter/encode times were respectively14.25/12.76/29.60/
28.48ms in this run; they are observations, not latency guarantees.
Per-phase averages now align exactly with target changes. At the0.5-Mbps
target H.264 QSV/VA-API actually produce about1.06/1.00Mbps. Hardware can
overshoot a small target; bitrate adaptation is not a strict wire-rate cap.

Static1970x1220/60, 600 frames, recovery IDR at347, ceiling8Mbps:
H.264 QSV, H.264 VA-API and HEVC VA-API all decode600 frames, have exactly
2 keys, and show no periodic static-text pulses. Peak mean text luma deltas
are0.014787/0.038298/0.0000123 out of255; threshold0.15. Initial0..90 and
requested-IDR347..437 refinement windows are excluded only from the steady
text metric, not decoding or keyframe checks.

HEVC QSV is NOT fully qualified: the same high-resolution static probe
fails at source frame51 with 'Invalid FrameType:0' / invalid encoded data.
It also fails as root, so this is not explained by the LXC privilege drop.
Disabling AUD, enabling LowDelayBRC or doubling VBV alone did not fix it.
LowPower=1 progresses further but fails at the requested IDR347, including
with a doubled VBV. None of those experimental options is shipped. A real
GPU test in the new Proxmox kernel remains outstanding; no claim is made
that a kernel update will fix this failure.

AMD regression on172.16.16.17, only standalone probes, no service changes:
HEVC VA-API with AUD=0 decodes1200 dynamic and600 static frames, with7/2 keys,
respectively. Static peak text luma delta0.002043/255. An initial static
fixture attempt could not read an absolute symlink through /root as nobody;
the public fixture was copied locally and the full test repeated successfully.
