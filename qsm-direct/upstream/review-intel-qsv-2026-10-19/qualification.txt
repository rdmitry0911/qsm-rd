Intel Iris Xe / nested Proxmox qualification, 2026-10-19
========================================================

Final implementation
--------------------
All four Intel encoders pass decoded-frame, bitrate-change, requested-IDR
and static-text checks: H.264/HEVC QSV and H.264/HEVC VA-API. The same shared
VM/LXC controller, pacing, status and configurable ceiling are used. The
native browser/LXC network checks below use H.264. HEVC remains experimental
at the browser level; no new Firefox HEVC playback claim is made.

1. QSV's live FFmpeg reset rejected the first8 ->2Mbps change with
   MFX_ERR_INCOMPATIBLE_VIDEO_PARAM(-14). Updating initial occupancy did not
   fix an HRD-buffer resize. QSV now drains/reopens just its codec on a
   material target change, retaining its prepared device, conversion,
   source timestamps and WebRTC peer, as VA-API already does.
2. Intel HEVC VA-API with AUD enabled emitted an escaped Annex B prefix,
   e.g.00 00 03 00 01 46 ... . Omitting redundant AUDs fixes all tested
   packets. In-process packets already delimit access units. Other codecs
   retain AUDs. The HEVC VA-API capability probe matches AUD=0.
3. HEVC QSV's high-resolution static CBR test failed at frame51 on both
   Ubuntu6.8 and Proxmox7.0. An LD_PRELOAD probe around the public VPL sync
   function records status-5, MFX_ERR_NOT_ENOUGH_BUFFER, before FFmpeg's
   'Invalid FrameType:0'. A one-second VBV passed but produced233kB IDRs,
   unsuitable for this interactive pipeline. LowPower/LowDelayBRC alone,
   doubled VBV alone and disabling AUD did not fix the original profile.
   The shipped HEVC-QSV-only profile uses VBR, LowDelayBRC=1, MaxFrameSize
   equal to one target frame and a two-frame VBV. MaxKbps is1kbit/s above
   TargetKbps to select FFmpeg's VBR mode. It decodes every tested frame,
   including explicit recovery IDRs, without the large-buffer workaround.
   H.264 QSV is unchanged. The HEVC QSV capability probe matches this profile.
4. The existing bounded low-rate NVENC pacing credit now also applies to
   QSV and VA-API. Intel H.264 can produce about1Mbps at a0.5Mbps target;
   pacing it at0.625Mbps caused FIFO overflow and repeated local recovery.
   The controller's target/hysteresis are unchanged. This is bounded pacing
   credit, not a higher encoder target or a strict total-wire-rate promise.
5. Explicit LXC VA-API policies now accept QSM_DIRECT_VAAPI_RENDER_NODE,
   validated with the same render-node pattern as VM policy. Previously
   the explicit encoder required a node, but the container parser rejected
   that key. Tests cover retaining the selection and rejecting other paths.

6. Final guest-package installation exposed an existing set -e failure:
   stopping absent transient session units aborted qsm-consoles. Unused
   slots now tolerate absent units; zero numbered ttys use the documented
   one-console fallback. Shell checks with 0/1/4/12 ttys pass, including
   failed inactive-slot stops; reinstallation on CT147 leaves qsm-consoles,
   qsm-display@1 and qsm-login@1 active. See console-startup logs.

Exact production-class probes
------------------------------
build-probes.py extracts LibavVideoEncoder from the current worker. The
included generated C++ sources link Trixie libavcodec61/7.1.5, libvpl2/2.14,
libmfx-gen/25.1.4 and Intel media driver25.2.3. Build with:
  g++ -std=c++20 -O2 encoder-probe.cpp -o encoder-probe \
      $(pkg-config --cflags --libs libavcodec libavutil libswscale)
  g++ -std=c++20 -O2 static-probe.cpp -o static-probe \
      $(pkg-config --cflags --libs libavcodec libavutil libswscale)
The dynamic probe takes CODEC 8000 nobody; the static probe takes CODEC
and always drops privileges. Create the device first, clear supplementary
groups, then uid/gid65534 before codec setup, encoding, resizes-equivalent
setup and rate changes. Explicit hardware probes have no software fallback.
QSV uses default Intel selection even with another vendor's render node;
VA-API uses QSM_PROBE_VAAPI_DEVICE or renderD128 in the test Proxmox VM.
The public fixture.bgra is generated by the existing keyframe-stability
review. On Ubuntu the Trixie libraries run in an isolated chroot, not over
the system libraries. Device node/group permissions are never changed.

Native Firefox / LXC network checks
-----------------------------------
Firefox runs headless on the physical Ubuntu host and opens the actual
Proxmox preview UI through18006. A PVE ticket travels over SSH stdin and
stays in memory, never logs. Port8007 is blocked and receives no request.
The fixture disables Firefox mDNS host-address obfuscation because slirp
cannot resolve the LAN multicast names; no production preference changes.
The earlier discarded mDNS attempt is retained. Actual UDP, capture,
hardware encoding, RTP, RTCP, decoding and the native PVE API are exercised.
The moving window is focused with Sway IPC; no fake video is substituted.
Explicit h264_qsv/h264_vaapi policy disables automatic CPU fallback.

Only VM UDP is limited20 ->3 ->20Mbps. After initial live video/motion,
3Mbps lasts25s and recovery lasts120s, with periodic browser counters.
Both begin/end with19/19 moving picture transitions and restore8/8Mbps
without reconnecting. Final reports:
  QSV:10156decoded,0decoder drops,166lost packets,3transition freezes
      totalling2.245s, final moving picture19/19, target8/8Mbps.
  VA-API:10191decoded,0decoder drops,163lost packets,4transition freezes

The last recovery reports add no freezes. Abrupt bandwidth loss can still
pause video during recovery; these are individual runs, not latency or
zero-freeze guarantees. The previous QSV pacing profile had11freezes/

low-target local FIFO starvation. Its shorter recovery schedule and different

0loss/0freezes. Only synthetic-video PNGs are public; full PVE inventory

Restoration and limits
-----------------------
After testing, shaping and the fixture are stopped, CT147's original auto/
8Mbps policy is restored, and the disposable VM is shut down to release
Intel. i915/SDDM are restored on the Ubuntu host and the automatic restore
timer is disabled. Its panel reports connected/enabled; VT framebuffer bind
is restored. Independent headless-xvfb/headless-plasma and the original VM
retain their processes. The test Proxmox VM is restarted without GPU;
CT147 is left on its normal login screen for later tests.

This release adapts bitrate, not resolution/FPS. Very low link capacities
may be below hardware's practical minimum; reduce size/FPS or use software.
HEVC-QSV-only VBR has1kbit/s MaxKbps headroom; the ceiling describes the
encoder target, not an exact wire cap. Hardware/driver/browser generations
beyond this test are not certified. The tests qualify the official in-process
libavcodec deb; the external-ffmpeg compatibility path is unchanged.
